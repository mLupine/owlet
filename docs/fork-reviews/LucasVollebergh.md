# LucasVollebergh/owlet main compared with ryanbdclark/owlet main

Research date: 2026-11-07. Read-only review from a unique temporary clone. No shared checkout, refs, remotes, project files, devices, or external communications changed.

## Practical findings

This fork is a substantial modernization of the same Smart Sock 2/3 integration. It adds stale-reading protection and diagnostics, improves setup/reconfiguration and token persistence, bundles its API implementation, and supplies optional dashboards and notification blueprints. It does not add another HA platform, local transport, camera support, or a new supported sock generation. Its cloud dependency remains.

The highest-value behavior change is that a successful HTTP poll no longer automatically means old measurements remain available. After five minutes without new cloud timestamps, applicable vitals become unavailable and a new diagnostic problem sensor turns on. A timestamp entity exposes the newest reading. A warning repair issue appears when the implementation's age condition exceeds one hour. Smart Sock 2 heart rate and oxygen are checked independently, so battery updates cannot keep a frozen heart-rate sensor available. However, the repair warning still uses the newest timestamp across properties: it can fail to warn indefinitely in that exact partial-staleness case.

The fork removes the external package requirement altogether. That fixes installation coupling and gives the integration ownership of HTTP/auth behavior, but also transfers API-client maintenance into this repository. The included client has concrete malformed-response and concurrent-token-refresh risks discussed below. Commit count is not correctness evidence.

## Implementation by feature

### Setup, lifetime and current HA APIs

`async_setup_entry` constructs one API object per account, authenticates, enumerates supported devices and constructs one coordinator per DSN. All coordinators share that API object. First refreshes run concurrently with `asyncio.gather`. Runtime state moves from `hass.data[DOMAIN][entry_id]` to typed `ConfigEntry.runtime_data`; all platform setup functions now read that location. This is an internal ownership change, not a config-storage migration.

`_async_store_tokens` reads the client's current token snapshot after discovery, filters falsey values and updates entry data only when something differs. This avoids relying exclusively on which earlier call happened to return refreshed tokens. During polls the coordinator still stores a returned `tokens` dictionary. Authentication/credentials exceptions become `ConfigEntryAuthFailed`; device enumeration with no supported sock becomes retryable `ConfigEntryNotReady` instead of setup returning false; network/client/timeouts and API errors become retryable setup/update failures. Unload removes outstanding stale repair issues after platform unloading succeeds.

Evidence: [`custom_components/owlet/__init__.py:43-108`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/__init__.py#L43-L108); [`custom_components/owlet/coordinator.py:57-175`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/coordinator.py#L57-L175). The coordinator is given `config_entry=entry`, enabling HA's coordinator lifecycle integration. Sensor/binary-sensor parallel updates are zero (coordinator driven), switches one. Entity descriptions become frozen dataclasses and platform callback typing is updated.

### Configuration and account behavior

`_async_login` centralizes authentication, validation, token retrieval and field/base errors. Login uses an email selector, region dropdown and masked password selector. New-account email whitespace is stripped and uniqueness is lowercased. It stores region, username and tokens, not the password. Reauthentication uses HA's entry helper and update/reload/abort helper instead of storing a mutable `reauth_entry` on the flow. A new `async_step_reconfigure` permits region changes and fresh login without deleting the entry; username stays fixed.

`OwletOptionsFlow` now subclasses `OptionsFlowWithReload` and does not assign to the HA-managed `config_entry` attribute. Polling edits therefore reload the integration. Scan interval defaults to 10 seconds and has minimum 5; this minimum was already present in upstream's schema despite old translation text saying 10. A new `stale_threshold` integer option defaults to 5 minutes, accepts 0–120, and zero disables freshness detection. Flow version remains 1; there is no `async_migrate_entry`. Existing entries lacking the new option use its default at runtime.

Evidence: [`custom_components/owlet/config_flow.py:71-249`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/config_flow.py#L71-L249); [`custom_components/owlet/const.py:10-50`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/const.py#L10-L50). The bundled `validate_authentication` checks only a devices endpoint status; it does not enumerate supported devices. Thus the login form's `no_devices` handler does not prove accounts without socks are rejected there; setup does the real filtering.

### Freshness, entities and repairs

`_property_updated_at` parses raw Ayla `data_updated_at`, independent of HA polling time. `last_updated` chooses the maximum timestamp among REAL_TIME_VITALS, HEART_RATE, OXYGEN_LEVEL and BATT_LEVEL. `reading_updated_at` uses the aggregate REAL_TIME_VITALS timestamp for V3; V2 heart rate and oxygen use their own properties, other readings use the maximum fallback. `is_stale` checks any present V2 vital independently. Charging or a known-off base station suppresses staleness; missing base state is treated as readings expected. Missing/unparseable timestamps are treated as not stale.

`OwletSensor.available` combines coordinator availability, charging policy and per-reading freshness. Binary sensors unavailable during charging use whole-sock freshness, meaning one frozen V2 vital can hide those alert entities too. Charging-compatible entities bypass freshness filtering. Sensor native values now use `.get`, and unmapped sleep states return `unknown` rather than raising KeyError. The oxygen average keeps the upstream 0–100 validity restriction, with an explicit None guard; the fork does not invent a new averaging algorithm.

Two unconditional diagnostic entities per sock are new: `<serial>-last_updated` (timestamp, translation name Last reading) and `<serial>-data_stale` (problem binary sensor). Existing sensor, binary-sensor and switch unique-ID formats retain serial/property keys, supporting registry continuity. Movement entities remain disabled by default. Signal strength becomes diagnostic. No new ordinary vital type is added.

`_async_update_stale_issue` creates a nonpersistent, nonfixable warning with a local-time last-reading string and deletes it when conditions clear; unload also deletes it. The condition measures timestamp age greater than one hour, not one hour elapsed since the five-minute threshold first tripped. It runs only after successful property updates, so a network failure does not independently create this repair. Evidence: [`custom_components/owlet/coordinator.py:57-175`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/coordinator.py#L57-L175); [`custom_components/owlet/sensor.py:129-233`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/sensor.py#L129-L233); [`custom_components/owlet/binary_sensor.py:130-193`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/binary_sensor.py#L130-L193).

### API client ownership and actual included behavior

Upstream's manifest pins `pyowletapi==2025.4.1`; the final fork has `requirements: []` and relative `.owletapi` imports. NOTICE identifies the included code as a copy of LucasVollebergh's pyowletapi-ng, derived from Ryan Clark's MIT-licensed client; a separate MIT LICENSE accompanies it. Its API, sock, constants and exceptions source is now inspectable in the integration. This review inspected that included implementation, but did **not** fetch or compare upstream's external 2025.4.1 package. Accordingly, features below are proven present in the fork, not all proven newly invented relative to that external package.

The client runs Firebase password verification/refresh, Owlet mini-token exchange and Ayla sign-in using regional endpoints. It recognizes specific email/password errors plus generic INVALID_LOGIN_CREDENTIALS. It refreshes expired/missing access tokens, applies a 60-second expiry margin, updates Authorization headers, and tracks changed tokens until devices/properties return them. `_request` refreshes and retries once for 401/403; persistent rejection becomes an authentication exception. Other non-200/201 statuses become connection errors. HTTP calls have a 30-second total timeout and network/timeouts are wrapped. This is a per-request limit, not a whole-poll deadline.

Device enumeration fetches properties for each candidate concurrently and detects V3 by REAL_TIME_VITALS or V2 by CHARGE_STATUS. Property reads and commands call APP_ACTIVE first. The optional activation interval can suppress repeated activation, but the integration never passes a nonzero interval: the default continues activation before every read/command. Do not credit this integration with reduced activation traffic.

Sock normalization maps aggregate V3 JSON fields (`hr`, `ox`, `bat`, `btt`, `rsi`, `oxta`, sleep/movement/charging/status fields) and separate V2 properties into the existing normalized schema. Base-station commands submit a JSON-string value containing timestamp and string true/false to BASE_STATION_ON_CMD. `OwletSwitch._async_set` catches OwletError as a translated HA exception and requests a coordinator refresh after sending; it does not verify that the eventual physical state equals the requested state. [`custom_components/owlet/owletapi/api.py:350-627`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/owletapi/api.py#L350-L627); [`custom_components/owlet/owletapi/sock.py:196-323`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/owletapi/sock.py#L196-L323); API_[`custom_components/owlet/const.py:10-50`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/const.py#L10-L50); [`custom_components/owlet/switch.py:70-100`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/switch.py#L70-L100).

The initial modernization temporarily introduced `compat.py`, handling missing external specific credential exception classes. The vendoring commit removes this shim and the external dependency path entirely. That compatibility layer is historical, not active final behavior.

## Compatibility and migration implications

Existing account keys and property-based unique IDs survive; no mandatory account deletion or entity recreation is encoded. Change repository ownership through HACS or replace the integration folder, then restart/reload as appropriate. Do not install two copies with domain owlet simultaneously. Existing customized entity IDs need dashboard editing regardless of matching unique IDs. New entries strip email whitespace; existing entries are not migrated to normalized usernames.

The explicit minimum moves to HA 2025.12.0; typed aliases also require a modern Python parser. Users on older HA should not assume the new API imports work. Vitals that formerly remained available can now become unavailable after five minutes, affecting automations, templates and statistics gaps. Stale can be disabled but that removes the protection. Alert availability also changes under stale conditions; users relying on alert state transitions should inspect automation behavior. Options changes now reload immediately. Vendoring removes PyPI installation/update dependency but updates to an external pyowletapi installation no longer affect this integration.

## Concrete potential defects and review concerns

1. **Medium: repair issue misses partial V2 freezes.** `is_stale` checks each vital, but the hour test subtracts `last_updated`, the maximum including BATT_LEVEL. Scenario: HEART_RATE remains two hours old while battery updates every minute. Heart rate is unavailable and Data stale on, yet no repair issue appears. Fix: compute age from the oldest stale expected vital, or track the actual transition into stale. [`custom_components/owlet/coordinator.py:57-175`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/coordinator.py#L57-L175).
2. **Medium: malformed cloud properties escape the coordinator's error boundary.** Sock V3 revision parsing requires `oem_sock_version`, valid JSON and `rev`; normalization converts values and strictly parses `%Y-%m-%dT%H:%M:%SZ`. Missing revision keys, null numeric fields, invalid JSON or fractional timestamp strings can raise KeyError/TypeError/ValueError, while coordinator catches only API/client/timeouts. This can break first setup or later refresh rather than producing controlled missing-data/UpdateFailed behavior. Confirmed source path; occurrence with real devices is unverified. Fix: validate at API normalization boundary and tolerate absent revision metadata. [`custom_components/owlet/owletapi/sock.py:196-323`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/owletapi/sock.py#L196-L323).
3. **Medium, conditional concurrency risk: shared API refresh has no lock.** Multiple sock coordinators share one API and run concurrently. `_request` calls authenticate without synchronization; expiry/rejection can initiate multiple refresh flows against shared header/token fields and reset the global changed-token flag. Whether refresh-token rotation causes an actual outage depends on server semantics not inspected. Fix: serialize token refresh and double-check expiry under a lock; snapshot changed tokens safely. [`custom_components/owlet/__init__.py:43-108`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/__init__.py#L43-L108); [`custom_components/owlet/owletapi/api.py:350-627`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/owletapi/api.py#L350-L627).
4. **Low/medium: unknown timestamps are explicitly treated as fresh.** Missing or malformed data_updated_at returns None, and `_is_old` returns false. Old numeric values can therefore remain available with freshness protection configured if the timestamp disappears. Also timezone-naive parsed timestamps can fail subtraction from UTC-aware time. The included normalizer has an additional stricter timestamp parse first for V3. Fix: define unavailable/unknown freshness separately from fresh. [`custom_components/owlet/coordinator.py:57-175`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/coordinator.py#L57-L175); [`custom_components/owlet/owletapi/sock.py:196-323`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/custom_components/owlet/owletapi/sock.py#L196-L323).
5. **Low/medium: stale-notification blueprint misses unavailable→on.** Startup into already stale state or recovery from a transport failure can make the problem sensor become on from unavailable. The blueprint's explicit from off excludes it. No notification occurs until a future off→on cycle; delayed state triggers also depend on HA restart/reload behavior. Fix: permit any transition to on, filtering startup intentionally if desired. [`blueprints/automation/owlet/owlet_stale_data_notification.yaml:44-85`](https://github.com/LucasVollebergh/owlet/blob/3314a7f9e08754b9e39d57cd8334b7db373ec1b9/blueprints/automation/owlet/owlet_stale_data_notification.yaml#L44-L85).

These are static findings or conditional risks, not claims of observed live failures. The bundled parser risks are newly owned code in this integration; without inspecting the old external package, their historical origin cannot be assigned to this fork.

## Tests and verification limits

The original tests were removed in the first modernization and replaced in the next commit using pytest-homeassistant-custom-component, MockConfigEntry, frozen time, mocked API objects and shared setup helpers. Coverage includes setup/unload failures and tokens, user/reauth/reconfigure/options flows, charging/stale entity availability, V2 per-vital behavior, repair issue creation/removal, switch command/error handling and diagnostics redaction. API tests use fake sessions for password login, expiration, rejected-token retry, response/network/timeout errors, device-version filtering, token propagation and activation intervals. Sock tests use included V2/V3 JSON fixtures to test normalized values and commands.

Blueprint tests validate HA automation configuration rather than deliver a phone notification. Dashboard tests walk entity references, translate Dutch suffixes against English registry expectations and handle area-prefixed IDs; they do not render the frontend or prove every card/feature exists on the minimum supported HA version. No screenshots were generated by this reviewer. Included screenshots are documentation artifacts, not this review's runtime evidence.

This review did not install dependencies or execute the pytest suite, make cloud calls with an Owlet account, run HA, test phones or operate devices. No pass count or coverage percentage is claimed. Static inspection supports code-path conclusions; vendor endpoint availability, device schema variation, token rotation, notification delivery, frontend rendering and minimum-version compatibility remain runtime checks. ## Candidates worth porting to mLupine

Highest priority: per-vital freshness plus diagnostic timestamp/problem entities, after fixing partial-freeze repair timing and unknown-timestamp policy. Port the behavior and tests together; decide whether hiding alert entities on a stale vital is the desired contract.

Next: OptionsFlowWithReload/runtime_data modernization, in-place reconfigure/reauth, retryable setup errors and robust token snapshot persistence. Preserve mLupine-specific entity identities and options rather than copying whole files blindly.

Useful support features: redacted diagnostics with JSON-string handling, truthful device metadata, translated command errors and optional phone blueprints. Expand redaction tests for future payload shapes. Dashboards are optional user-facing examples that can be copied independently after checking entity naming and frontend versions.

Vendoring is a separate maintenance decision. It supplies inspectable ownership and tests, but should be taken only with parser validation and synchronized authentication; retaining an independently maintained pinned client may be preferable depending on mLupine's current design. This review did not inspect mLupine's code, so these are candidates, not verified clean cherry-picks.
