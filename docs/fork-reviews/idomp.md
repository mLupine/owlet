## Practical behavior changes

1. Modern HA integration lifecycle replaces older setup patterns. Options reload correctly, failed credentials trigger reauthentication, and region can be changed without deleting the account entry.
2. Old cloud readings no longer masquerade as live measurements by default. Five-minute freshness checks hide stale sensors and alerts; diagnostic entities explain why. A successful HTTP request alone does not imply fresh measurements.
3. HA loses the base-station on/off switch. Its registry entries are actively deleted during setup, and the replacement is an observational binary sensor. Automations calling the switch break.
4. The integration ships its own API client instead of installing upstream `pyowletapi==2025.4.1`. This permits substantial networking, decoding and activation changes locally, but moves client maintenance into this repository.
5. Default new-account polling slows from five to ten seconds. APP_ACTIVE writes default to every thirty seconds, with an immediate write when the returned APP_ACTIVE state says the base went idle. Reading data precedes the activation write.
6. Dream Sock/Smart Sock 3 decoding becomes tolerant of malformed values and exposes additional status/alert fields. Smart Sock 2 heart rate and oxygen each have freshness checks.
7. Included dashboards, phone-notification blueprints, diagnostics, Dutch translations and repair warnings add operator-facing tooling. Ukrainian translations are removed.

## Implementation by feature

### HA lifecycle, accounts and options

Upstream stores coordinators under `hass.data[DOMAIN][entry_id]`; the fork uses a typed `ConfigEntry.runtime_data` dictionary keyed by device serial. Setup authenticates, enumerates compatible versions 2/3, initializes one coordinator per sock concurrently, stores tokens, removes obsolete switch entities and forwards only sensor/binary_sensor platforms. No-devices setup now raises `ConfigEntryNotReady` rather than returning false. Shared HA aiohttp session remains in use; normal unload does not close that shared session.

[custom_components/owlet/__init__.py:44-164](https://github.com/idomp/owlet/blob/2bd5f61c1f1c12734c75cdda0f8e0873d6b52e68/custom_components/owlet/__init__.py#L44-L164)

`account_unique_id()` builds `region_username.strip().lower()`. Entry version increases from 1 to 2 and migration updates the existing entry rather than recreating it. This permits the same email in Europe and World and makes whitespace/case duplicates less likely. Login now verifies that supported socks actually exist using `get_devices`, rather than merely validating the token. `_async_login()` centralizes field-specific password/email errors, generic credential errors, rate-limit errors, network errors and unexpected errors. Reauth asks only for the password; reconfigure permits region/password with duplicate-account checking and reload. Password is used for authentication, not stored in entry data: entry retains username, region, API token, expiry and refresh token.

[custom_components/owlet/config_flow.py:77-296](https://github.com/idomp/owlet/blob/2bd5f61c1f1c12734c75cdda0f8e0873d6b52e68/custom_components/owlet/config_flow.py#L77-L296)

Options are `scan_interval` (integer seconds, minimum 5), `stale_threshold` (integer minutes 0–120; 0 disables freshness gating), and `activation_interval` (integer seconds 10–600). Defaults are 10 seconds, 5 minutes and 30 seconds. Existing saved polling options remain; absence gets fallback defaults. `OptionsFlowWithReload` applies options by reloading. Entity-description dataclasses become frozen, callback types and coordinator typing are updated, and `PARALLEL_UPDATES=0` is declared on entity platforms. Icons move from descriptions into `icons.json`.

### Freshness, availability and repair issues

`parse_reading_timestamp()` accepts only parseable timezone-aware cloud timestamps, converts to UTC, rejects missing/invalid timestamps and timestamps more than 60 seconds in the future. For v3 the source is REAL_TIME_VITALS.data_updated_at. For v2 heart rate and oxygen use their own raw property timestamps; the aggregate newest timestamp considers heart rate, oxygen and battery. It never derives freshness from the local polling time.

`reading_available()` hides all data-backed entities once their mapped reading is stale; ordinary vitals are hidden while charging too. Diagnostic last-updated and stale-state entities remain separate. `readings_expected` remembers whether the last fresh reading said charging or base off; stale warnings are suppressed in those intentional idle states, although old values remain hidden. This state is in-memory and resets at reload. `OwletStaleSensor` supplies `reading_status`, `last_reading`, `age_seconds`, `readings_expected` attributes. A local callback pushes an update at the aggregate reading's expiry rather than always waiting for the next poll.

[custom_components/owlet/coordinator.py:48-376](https://github.com/idomp/owlet/blob/2bd5f61c1f1c12734c75cdda0f8e0873d6b52e68/custom_components/owlet/coordinator.py#L48-L376)

Repair issues use `stale_data_<serial>`, warning severity, nonpersistent and nonfixable; an issue is created when stale and the aggregate last-reading timestamp is more than an hour old. It is deleted on recovery/unload. That is an age-of-reading rule, not literally one hour after crossing the configurable stale threshold. If no usable timestamp ever exists, this repair issue is never created. See the defects below for incomplete per-property and timer handling.

### Bundled client, authentication, retry and activation

`NOTICE` attributes the integration to Ryan Clark and the intervening Lucas Vollebergh fork; the bundled MIT client is attributed to pyowletapi-ng/lucasvollebergh/pyowletapi. The manifest no longer has a pip requirement and identifies idomp as maintainer, with version 2026.10.1, integration type hub and cloud_polling. This review inspected the bundled client; it did **not** independently inspect the installed contents/behavior of upstream's external pyowletapi 2025.4.1 or the external pyowletapi-ng source revision. Added client code is therefore established as fork-owned behavior, not automatically a demonstrated behavioral regression/fix relative to every upstream library implementation.

The bundled client authenticates through Google password/refresh services, Ayla mini-token exchange and token sign-in. An asyncio lock serializes normal expiry-based authentication across socks sharing the client. HTTP requests have a 30-second timeout. Request-layer 401/403 invalidates the access token and retries after refreshing once; a second rejection raises authentication error. 429 becomes `OwletRateLimitError`; >=500 becomes transient connection error. Retry-After accepts seconds or HTTP date, clamped to 5–3600 seconds. Login TOO_MANY_ATTEMPTS maps to a 900-second transient delay. JSON decoding failures and missing expected login tokens become connection failures rather than silently accepted responses.

[custom_components/owlet/owletapi/api.py:244-795](https://github.com/idomp/owlet/blob/2bd5f61c1f1c12734c75cdda0f8e0873d6b52e68/custom_components/owlet/owletapi/api.py#L244-L795)

The coordinator catches credential exceptions as `ConfigEntryAuthFailed`; transient failures become `UpdateFailed(retry_after=...)`. Backoff doubles the base polling interval by consecutive failure count, nominally caps at five minutes, then applies 0.8–1.2 jitter and respects longer Retry-After. Thus the actual jittered ceiling can reach six minutes. Tokens are persisted in the coordinator's `finally`, including refreshes during failed polls. Successful refresh resets failure count.

The only permitted property write is APP_ACTIVE. `_request()` refuses other non-GET property calls; login POST requests use separate authentication paths. The previous Sock on/off methods and switch platform disappear. Discovery checks device properties without activation. Polling fetches properties first, then awaits `_activate_quietly()`. Activation records monotonic time only after success and is forced when APP_ACTIVE is 0/false, including supported string representations. A failed transient activation is logged and retried next poll. The final commit changes the earlier 60-second default to 30 seconds and overrides the cadence when idle. The source's claim of roughly 45 seconds of base uploading is an author-reported device observation, not a measurement reproduced here.

### Value decoding and entities

`decode_bool` recognizes string booleans, numbers and actual bools; unknowns become None. Numeric decoders reject nonfinite values and malformed strings; integer decoder requires whole floats. Vitals JSON must be an object. Bad JSON makes vitals unknown and logs a warning once until recovery. Valid fields survive individual malformed neighbors. Range checks convert HR outside 1–300, oxygen/10-minute average outside 1–100 and skin temperature outside 1–60 to unknown. The latter ranges are implementation choices, not medically validated bounds established by this review. Version detection retries when initial properties cannot identify a sock; v3 hardware revision parses `oem_sock_version` JSON.

New generic binary entities cover base_station_on, critical battery/oxygen, discomfort, low_integrity_reading and four preview priority alarm properties. Additional numeric diagnostic sensors expose alerts_mask, BASE_MON_STATUS and BATTERY_STATUS. New timestamp sensors show latest reading and, conditionally, RED_ALERT_SUMMARY's update time (not independently decoded clinical alert time). ### Diagnostics, dashboards, notifications and packaging

New diagnostics include only region/options from the entry, anonymized sock indices, model/software/version fields, freshness state and normalized properties. Raw property values use an allowlist; other raw values are REDACTED and only base_type/direction/data_updated_at are retained. Earlier generic recursive/JSON redaction is superseded. This is safer against new unknown property names, but not a recursive content allowlist inside known JSON properties such as REAL_TIME_VITALS. Also malformed-vitals warning logs can still include raw payloads and serials, outside the diagnostics sanitizer.

English/Dutch dashboard YAML and screenshots are delivered as manual-install artifacts; they are not automatically provisioned into HA. Dashboards use templating/discovery and conditional views for live readings, sleep and trends. The Dutch dashboard adds more extensive presentation. Alert blueprint sends Companion app device notifications (optionally critical) only on off→on. Stale blueprint notifies after optional extra minutes and optionally on on→off recovery. That transition filter prevents restart/unavailable reappearance from generating a new alert, but also intentionally misses an alarm first seen active after an outage. Selectors are broader than precise semantic keys, so choosing an unsuitable binary sensor is possible.

## Concrete findings and migration risks

### High: v2 non-vital entities can still display stale values under a fresh aggregate timestamp

`reading_updated_at()` maps only heart_rate/oxygen_saturation individually; every other key returns newest HR/oxygen/battery timestamp. A Smart Sock 2 whose HEART_RATE keeps updating but whose BATT_LEVEL or HIGH_HR_ALRT freezes retains an apparently available old battery/alert state. Likewise v3 standalone alert timestamps are ignored in favor of REAL_TIME_VITALS. This contradicts the broad claim that everything stale is hidden. Fix by mapping each normalized property to its actual raw source, with explicit semantics for independently updated/event-driven properties, and test mixed-age snapshots. Evidence: coordinator lines 224–245, 269–282; owletapi/const.py PROPERTIES/VITALS_2 mappings. This is a confirmed source-level behavior; whether particular cloud properties freeze independently requires device evidence.

### Medium: expiry callback follows newest v2 timestamp, not earliest entity deadline

`_schedule_expiry()` schedules only `last_updated + threshold`; `last_updated` is max for v2. With long user-configured polling, HR can expire before newer oxygen/battery and remain displayed until the later callback or next poll. Fix by scheduling the nearest future expiration among entity-specific timestamps, then reschedule remaining deadlines. Evidence: coordinator lines 224–245 and 346–369. No upper bound on scan_interval makes the gap potentially much longer than default polling.

### Medium: activation still delays a successful read and can discard it on auth failure

`_fetch_properties()` awaits activation before returning the already-read snapshot. A stalled activation can delay display by the request timeout and authentication exchanges. `_activate_quietly()` catches only OwletConnectionError, not OwletAuthenticationError; a rejected activation after a successful GET can therefore fail the whole poll and trigger reauth. “Never blocking it” is stronger than the implementation. Fix by explicitly separating read publication and activation lifecycle, or at least catching/handling activation authentication failures without losing the read. Evidence: api.py lines 692–724, 755–773. Do not casually background the write without cancellation/ownership handling.

### Medium: refreshed credentials can be lost during setup failure

Setup persists tokens only after both authenticate and get_devices succeed. If refresh rotates a token, then discovery fails, execution exits through an exception without `_async_store_tokens()`. Coordinator finally persistence does not cover this setup phase. A restart can reuse stale stored credentials. Fix by persisting available tokens in a setup finally path just as polling already does. Evidence: __init__.py lines 97–118 versus coordinator lines 101–139. This depends on server token-rotation semantics; the persistence omission itself is definite.

### Medium: partial v3 first snapshot permanently omits later entities until reload

For valid REAL_TIME_VITALS JSON, absent keys are omitted from normalized properties. Entity creation tests key membership only once. If initial snapshot lacks `ss`, `ox` or a newly appearing status property and later snapshots include it, the corresponding entity never appears in that session. Fix by defining capability-based entity creation or adding entities as capabilities arrive; test partial-first/complete-second snapshots. Evidence: sock.py lines 321–339; sensor.py lines 127–148; binary_sensor.py lines 141–161. This partly inherits upstream's key-presence setup design; the new fields expand exposure.

### Medium/operational: silent repair and notification gaps

With no timestamp, stale sensor can be on but repair never appears because `_async_update_stale_issue` requires last_updated. With one old v2 vital and another continually updating, aggregate timestamp never exceeds an hour, so no repair appears even though is_stale is true. Repair evaluation occurs on successful polls/expiry, not a dedicated one-hour timer. If a last-fresh charging/off state is remembered, stale warnings stay suppressed indefinitely until fresh data resumes; reload resets the expectation and can change that visible state. Off→on-only blueprints also miss initial on/unavailable→on conditions by design. These are policy choices/edge cases requiring explicit acceptance, not proof the base station's own alarm is affected.

### Compatibility decisions

Upgrade in-place should retain established sensor identities and credentials, but makes an entry schema-v2 change and removes switches. Back up HA configuration before moving between forks; old upstream has no demonstrated v2 downgrade migration. Replace switch-service automations with observational conditions or remove their control action. Do not assume entity friendly names and generated IDs stay identical on a fresh installation: translation/model/category changes can affect initial naming. Ukrainian UI translations fall back to another language. HA 2025.12 compatibility advertised early in history is superseded by current HACS minimum 2026.10.0 and a test stack for 2026.10.1; current source is not verified on 2025.12.

## Tests and verification limits

The rewritten suite covers config user/reauth/reconfigure/options and migration, setup/unload and switch cleanup, coordinator timestamps/stale masking/expiry/backoff/token persistence/repairs, sensor/binary state, diagnostics and YAML blueprints/dashboards. Bundled-client tests exercise authentication/status classification/activation cadence and typed decoding using v2/v3 JSON fixtures. These are useful unit/integration mocks, not evidence that Owlet's cloud, physical devices, notifications or displayed dashboard rendering work in production.

No HA test suite was run in this research task; no dependencies were installed, no cloud credentials used and no devices touched. CI configuration and test source were inspected; the 93% floor is a configured requirement, not a coverage measurement obtained here. No assertion is made that current GitHub Actions runs passed. The upstream external API package and HA internals were not independently audited; lifecycle observations depending on those remain bounded accordingly.

## Candidate ports to mLupine

1. Port the frozen descriptions, runtime_data lifecycle, safe awake/sleep handling, field-specific login errors and region/email identity migration after checking mLupine's existing schema/IDs. These are narrow and useful.
2. Port typed/sentinel decoding with fixtures and explicit device capability creation. Preserve unknown rather than making up valid-looking measurements.
3. Port cloud-timestamp freshness and stale diagnostics, but first correct per-property mappings, earliest-expiry scheduling and mixed-age repair logic. Copying the entire freshness implementation unchanged imports known gaps.
4. Port transient status classification, one-refresh retry and Retry-After backoff, plus token persistence in both setup and polling. Add concurrent-401 tests; the normal auth lock does not alone prove all invalidation races safe.
5. Consider an APP_ACTIVE-only write policy and switch removal as an explicit product decision. This breaks control automations and must not be snuck in as routine maintenance. Validate the thirty-second/idle-reactivation policy on each supported model/firmware before treating author-reported Dream Sock timing as universal.
6. Diagnostics allowlisting and the build/test/release scaffolding are worthwhile. Add actual `ruff check`, test supported HA minimums, and recursively sanitize known JSON content if privacy guarantees require it. Dashboards and blueprints are optional examples, with their missed-transition semantics documented.
